# Generating API clients

> Every Strata deployment serves an OpenAPI 3 document at `/v3/api-docs`; generate typed clients instead of hand-writing
> fetch wrappers.

## Get the spec

```bash
curl -s https://admin.example.com/v3/api-docs -o openapi.json
# local dev
curl -s http://localhost:8080/v3/api-docs -o openapi.json
```

The document is generated by springdoc from the controllers and carries the framework version, so you can archive the
spec per deployment.

## TypeScript / JavaScript

```bash
# types only (tiny, zero runtime)
npx openapi-typescript openapi.json -o src/api/schema.d.ts

# or a full fetch client
npx @hey-api/openapi-ts -i openapi.json -o src/api/client
```

The admin console itself uses TanStack Query over small typed modules; generating types only is usually the sweet spot.

## Java / Kotlin

- **Maven**: `openapi-generator-maven-plugin` with `generatorName=java` or `kotlin` and `library=restclient`/native.
- **Gradle**: `org.openapi.generator` plugin, same generator names.
- Keep the generated client in a separate module so the generator output never mixes with hand-written code.
- Authenticate by adding the `Authorization: Bearer <token>` header; login endpoints are under `/api/v1/system/auth/*`.

## Other languages

`openapi-generator` supports python, go, csharp, php, ruby, dart and more with the same spec:
`npx @openapitools/openapi-generator-cli generate -i openapi.json -g python -o clients/python`.

## Contract stability

- `*-api` DTOs are the public contract; breaking changes follow the [upgrade guide](./upgrade-guide.md).
- Pin the generated client to a spec version and regenerate on release upgrades — diff before committing.
- Error bodies are RFC 7807 `ProblemDetail`; success bodies are `Result<T>` — model both in the client.
